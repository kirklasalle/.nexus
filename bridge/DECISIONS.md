# Nexus Bridge Decisions

Record decisions here when they should outlive a single thread update.

| ID | Date | Decision | Status | Owner | Rationale |
| --- | --- | --- | --- | --- | --- |
| ADR-001 | 2026-03-06 | The canonical write rule for new bridge updates is append-to-bottom. | Active | VS Code Copilot | Existing files contained both append and prepend instructions; one rule is required for reliable operation. |
| ADR-002 | 2026-03-06 | `hotline.md` remains the broadcast channel, while dedicated threads handle directed collaboration. | Active | VS Code Copilot | The hotline is useful for shared visibility, but it should not replace targeted threads. |
| ADR-003 | 2026-03-06 | Foundational operating docs are required for the bridge itself. | Active | VS Code Copilot | The bridge had design intent but lacked task, onboarding, ownership, and decision artifacts. |
| ADR-004 | 2026-03-06 | Shared assets belong under `Shared_Assets/` and must be referenced from thread entries. | Active | VS Code Copilot | Shared material should be discoverable and should not fragment into ad hoc locations. |
| ADR-005 | 2026-03-06 | Active threads archive monthly using `Thread_Archive_YYYY-MM.md`. | Active | VS Code Copilot | A predictable archive cadence keeps active threads readable without rewriting history. |
| ADR-006 | 2026-03-06 | Bridge structure and protocol changes should be checked with `tools/Validate-Bridge.ps1`. | Active | VS Code Copilot | Lightweight automation reduces protocol drift and catches missing files or contradictory instructions. |
| ADR-007 | 2026-03-06 | Nexus should operate from a dedicated playbook and reusable message templates. | Active | VS Code Copilot | The bridge needs teachable operator behavior, not just reference docs, so the system can scale without relearning the workflow each time. |
| ADR-008 | 2026-03-06 | The bridge should maintain a one-page status dashboard in `STATUS.md`. | Active | VS Code Copilot | Nexus needs a fast way to understand health, open work, and validation state without reading multiple files first. |
| ADR-009 | 2026-03-06 | Monthly thread rollover should be performed through `tools/New-BridgeArchive.ps1` when practical. | Active | VS Code Copilot | Rollover steps are easy to drift when done manually; a helper script makes the archive policy repeatable. |
| ADR-010 | 2026-03-06 | Nexus is considered operationally done after one clean monthly bridge cycle using status, tasks, decisions, validation, and archive preview correctly. | Active | VS Code Copilot | The bridge needs a measurable finish line so training can end and readiness can be evaluated objectively. |
| ADR-011 | 2026-03-06 | Nexus readiness should be evidenced by a certification checklist and a completed monthly review record. | Active | VS Code Copilot | A finish line is more credible when it produces an auditable sign-off artifact rather than a verbal claim. |
| ADR-012 | 2026-08-08 | The canonical governance charters are the three platform-root files — `Permanent_Active_Directives.txt` (supreme, immutable), `AGENTIC_PRIME_DIRECTIVE.md` (v3.1.0), `AGENTIC_SACRED_COVENANT.md` (v2.0) — pinned by SHA-256 in `charter_manifest.json` and verified by the bridge validator (FAIL on drift). Legacy `COPILOT_PRIME_DIRECTIVE.md` / `COPILOT_SACRED_COVENANT.md` are superseded and removed (originals recoverable from ImpressionCore archives). PRISM-scoped wording is interpreted as governing all projects and participants coordinated through this bridge. Covenant Article III mechanisms not yet implemented here (attestation, approval tokens, hash-chained ledger) are roadmap v4.0 — the manifest + validator gate is the honest bridge-level subset. | Active | Kirk_LaSalle / VS_Code_Copilot | Replaces the deprecated-vs-active trust-object ambiguity (audit NX-11, PrismRefraction IC-08 class) with one pinned constitution and an enforced amendment ritual. |
| ADR-013 | 2026-08-08 | Hotline severity is expressed as a color ladder inside the single canonical `bridge/hotline.md` — subject prefixes `[RED]` (stop-the-line; all-recipient ack ≤15 min of next activation; only Kirk de-escalates), `[AMBER]` (act-soon; owner ack same session), `[YELLOW]` (caution; auto-escalates to AMBER if unacked 48h), `[GREEN]` (all-clear; only closure mechanism), `[BLUE]` (operator directives; Kirk_LaSalle only). Color-named hotline files (e.g., `RED_HOTLINE.md`) may exist in v3.0+ only as auto-generated projections, never hand-written — one master file prevents split-brain recurrence (NX-02). | Active | Kirk_LaSalle | One paging channel with severity levels (SRE/PagerDuty pattern) preserves the color taxonomy's value without multiplying divergence surfaces. Ratified by the Founder 2026-08-08. |
